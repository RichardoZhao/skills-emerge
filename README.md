# Skills-Emerge

> **一句话：把重复的技能合并掉，把互补的留下来。**
>
> 你的 AI agent 技能库装到几十上百个时，必然出现"这个跟那个好像是一回事"。
> 这个技能包给你一套**能落地执行的判断流程** —— 哪两个该合、哪两个看着像其实不该合、
> 合并时怎么不丢东西、合完怎么验证真的没问题。

**它不是一个自动合并工具。** 它出判据和清单，最终取舍由你定。

**它不提供技能，也不收录技能** —— 它只管你**已经攒下的那几十上百个**。
（如果你在找"技能商店"或"技能清单"，这里不是。）

## 它解决什么问题

关心 agent 技能库的人有个共同的困境：

```
· 装了 50+ 个 skill，开始分不清哪个是哪个
· 同一个功能有两三个版本，不知道留哪个
· 想合并，又怕把独有的知识丢掉
· 合完之后不敢删原文件，于是库越来越臃肿
· 更糟的是：两份 skill 对同一个动作给了矛盾指令，合并后 agent 开始"精神分裂"
```

**这个技能包做的事**：给你一张判断表（五类重叠，各配处置方式）、一套六步流程、
和九条**真踩过的坑**。

## 里面最有价值的三样东西

### 1. 判定表 E 类：冲突 ≠ 重叠

我见过的主流去重方法大多只处理**重复**，很少识别**矛盾**。

```
重叠：两份讲了同一件事        → 去重选优即可
冲突：两份对同一动作给出相反指令 → 硬合会让 agent 收到打架的指令，比不合更糟
```

这一条把"合并"从"挑最全的那份"升级成"要么分支化，要么别合"——
**这是判断力，不是流程。**

### 2. 九条实测坑（含两条反直觉的）

比如这两条，都是别人容易踩的：

> **同名 ≠ 重复。** 不同目录下的同名 skill 可能内容完全不同，先看再判。
>
> **粒度不统一会误判重叠。** A 拆 3 步、B 拆 10 步没法比。
> 比对前先把两份都摊成同粒度（一个步骤＝一次不可再分的动作）。

### 3. 第 5 步的"行为验证"标准

删完文件之后，怎么知道合对了没？

> **合并后的 skill 必须能独立完成至少一个「原被删 skill」的完整任务**
> （拿原 skill 的触发语去测）。做不到，就不许删原件。

**合并出错是"看不出来"的错** —— 文件在不在说明不了问题。这条标准把验证变成可判定的。

## 一次真实的收敛结果

**技能库从 395 个降到 379 个**（合并掉约 4%）。

> 口径说明：这是作者个人工作间的技能库规模，不含任何业务数据、客户信息或个人信息。

过程记在 `SKILL.md` 的「实战案例」一节。
其中最值得看的是那几组**"看起来该合、其实该留"的互补对** ——
合并它们省不了多少开销，却会让触发面变宽、误触发率上升。

## 产品边界（不做的事）

| 不做 | 原因 |
|---|---|
| 自动合并 | "怎么合并"可以标准化，"具体保谁"必须具体判断 |
| 改内容 | 那是新 skill 创作，不是融合 |
| 重写功能 | 融合只做"合并同类项" |
| 帮你备份 | 流程强制要求留回滚点，但执行是你的事 |

## English Summary

**Skills-Emerge** is a decision procedure for consolidating an AI agent's skill library:
which skills to merge, which look similar but must stay separate, how to merge without
losing information, and how to verify the result afterwards.

It is a **governance tool, not a skill marketplace** — it manages the skills you already
have. The core asset is a five-type overlap table (including a *conflict* category that
most dedup methods miss), a six-step procedure, and nine field-tested pitfalls.
